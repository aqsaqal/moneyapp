# Release playbook — App Store and Google Play

Written from shipping Flow (Expo / React Native) through TestFlight, App
Store review, Play closed testing and Testers Community. Reusable for a new
app: swap the identifiers in the first section. No secrets in this file.

Accounts needed once: Apple Developer Program (paid, yearly), Google Play
developer account (one-time fee), signed agreements in both consoles
(Apple's "Paid Apps" agreement is needed even for free apps before uploads
succeed; Google asks for a trader-status declaration).

Keystore (once per app):

```bash
keytool -genkeypair -v -keystore ~/.android-keystores/<app>-upload.jks \
  -alias upload -keyalg RSA -keysize 2048 -validity 10000
# then in ~/.gradle/gradle.properties:
# MONEYFLOW_RELEASE_STORE_FILE=/Users/<you>/.android-keystores/<app>-upload.jks
# MONEYFLOW_RELEASE_KEY_ALIAS=upload
# MONEYFLOW_RELEASE_STORE_PASSWORD=...
# MONEYFLOW_RELEASE_KEY_PASSWORD=...
```

Never commit the keystore or the properties. Losing the keystore means a
new package name; back it up.

## 1. Versioning

`app.config.ts` holds three numbers; bump all three per store release:

- `version: '1.2.0'` — marketing version, both stores.
- `ios.buildNumber: '4'` — Apple uniques on this; must increase every upload.
- `android.versionCode: 4` — Play uniques on this; must increase every upload.

The native projects (`ios/`, `android/`) are gitignored and regenerated by
`expo prebuild`. If you don't re-run prebuild after a bump, also patch
`ios/<App>/Info.plist` (`CFBundleShortVersionString`, `CFBundleVersion`),
or the archive will carry the old version.

Commit the bump as its own commit: `release: bump to X.Y.Z (iOS build N / Android versionCode N)`.

## 2. iOS: archive, export, upload

Prerequisites: Xcode installed, signed in to the Apple ID in Xcode, pods
installed (`npx pod-install` after prebuild).

```bash
# 1. Archive (device build, automatic signing)
xcodebuild -workspace ios/<App>.xcworkspace -scheme <App> -configuration Release \
  -destination 'generic/platform=iOS' -archivePath build/<App>-X.Y.Z.xcarchive \
  archive DEVELOPMENT_TEAM=<TEAM_ID> -allowProvisioningUpdates

# 2. Export an IPA (destination=export) — optional, for a local artifact
xcodebuild -exportArchive -archivePath build/<App>-X.Y.Z.xcarchive \
  -exportOptionsPlist build/ExportOptions-export.plist \
  -exportPath build/<App>-export-X.Y.Z -allowProvisioningUpdates

# 3. Upload to App Store Connect / TestFlight (destination=upload)
xcodebuild -exportArchive -archivePath build/<App>-X.Y.Z.xcarchive \
  -exportOptionsPlist build/ExportOptions-upload.plist \
  -exportPath build/<App>-upload-X.Y.Z -allowProvisioningUpdates
```

ExportOptions.plist (the two files differ only in `destination`):

```xml
<dict>
  <key>method</key><string>app-store-connect</string>
  <key>destination</key><string>upload</string>   <!-- or export -->
  <key>signingStyle</key><string>automatic</string>
  <key>teamID</key><string>TEAM_ID</string>
  <key>uploadSymbols</key><true/>
  <key>manageAppVersionAndBuildNumber</key><true/>
  <key>stripSwiftSymbols</key><true/>
</dict>
```

Notes:
- Archive takes 3–8 minutes; run it in the background.
- "requires a development team": pass `DEVELOPMENT_TEAM` and set `appleTeamId`.
- "PLA Update available" / "No signing certificate iOS Distribution": a new
  agreement is waiting in the Apple Developer account; accept it in the
  browser and re-run the export.
- Missing dSYM warnings for Hermes / ReactNativeDependencies are harmless.
- Processing after upload takes 5–20 minutes; the build then appears under
  TestFlight and in the version's build picker.

## 3. App Store Connect: the version

1. Apps → the app → iOS App → **+** → New Version (e.g. `1.2`).
2. What's New (up to 4,000 characters; bullets with `•` render fine).
3. Build → **Add Build** → pick the processed build.
4. App Previews and Screenshots: the required slot is **iPhone 6.3"**
   (1206×2622 or 1179×2556). Upload the other sizes in "View All Sizes in
   Media Manager": **6.9"** 1320×2868 (iPhone with Dynamic Island, large),
   **6.5"** 1284×2778 (iPhone with Face ID, large). Max 10 per slot.
   Uploads save immediately; "Remove All" clears a slot.
5. Save. Then **Add for Review** → **Submit to App Review**.

Blocking checks seen so far:
- **Age ratings**: Apple adds questions over time (Social Media, Shared
  Location, Dating…). "Unable to Add for Review" with a link to App
  Information → Age Ratings → Edit → walk all 7 steps → Save.
- App Review Information: contact details and notes; mention a demo
  profile or test path so the reviewer can see data.

Review usually takes 1–2 days. "Automatically release this version" is the
default; switch to manual if you want to time the release.

## 4. Android: build an AAB

```bash
bash scripts/build-aab.sh generic     # Flow's script; copies to /tmp/generic-release.aab
```

What the script does, for a new app:
1. `expo prebuild --platform android --no-install --clean` (regenerates `android/`).
2. Writes `android/local.properties` (`sdk.dir=$HOME/Library/Android/sdk`).
3. Injects a `release` signingConfig into `android/app/build.gradle` that reads
   `MONEYFLOW_RELEASE_*` from `~/.gradle/gradle.properties`, and points the
   release buildType at it. The Expo template signs release with the debug
   keystore otherwise, which Play rejects.
4. `./gradlew app:bundleRelease` → `android/app/build/outputs/bundle/release/app-release.aab`.
5. Checks the bundle is not debug-signed. Config plugins can rewrite
   `build.gradle` (expo-iap normalizes `signingConfig signingConfigs.debug`
   to `signingConfig = signingConfigs.debug`); the script handles both
   spellings, and a debug-signed APK will not install over the store build
   ("signatures do not match").

For a local APK to sideload: `./gradlew app:assembleRelease` then
`adb -s <serial> install -r android/app/build/outputs/apk/release/app-release.apk`.
Run gradle and adb plainly, without `PATH=`/`ANDROID_HOME=` prefixes (those
get denied in the sandbox); `$HOME/Library/Android/sdk/platform-tools/adb`
works as an absolute path. Check `adb devices`: "unauthorized" means the
phone's USB-debugging prompt hasn't been accepted.

Config that avoids Play warnings (in `app.config.ts`):
- `expo-build-properties` → `android.enableProguardInReleaseBuilds: true`,
  `enableShrinkResourcesInReleaseBuilds: true`, plus `extraProguardRules`
  for libraries that reflect at runtime (MMKV, ML Kit, Skia, Expo modules).
  Otherwise Play flags "DEX code optimization below threshold".
- A config plugin that declares `android.hardware.camera` (and `.autofocus`)
  with `required="false"` if the app has the CAMERA permission; otherwise
  Play treats the camera as required and warns on every submission.
- Expect advisory warnings about deprecated edge-to-edge APIs (dependency,
  clears with SDK upgrades) and orientation locks on large screens.

## 5. Play Console: first release and testing

Google requires a **personal** developer account to run a closed test with
12+ testers for 14 days before it can publish to production.

1. Test and release → Closed testing → create a track (e.g. Alpha) →
   **Create new release** → upload the AAB (large bundles take minutes to
   upload and then "optimize") → release notes (**500 characters max**, wrapped
   in `<en-US>…</en-US>`) → Next → Save.
2. Track → **Testers** tab: Google Groups → add
   `testers-community@googlegroups.com` → Save. Countries: all.
3. The opt-in link is `https://play.google.com/apps/testing/<package>`.
4. Store listing → Edit default listing → Phone screenshots (2–8, 16:9 or
   9:16, e.g. 1080×2340). Assets go through the asset library side panel:
   Upload, then select in the desired order, then Add. Save.
5. **Publishing overview** → "Submit N changes for review" → confirm.
   Everything saved (release, testers, listing, pricing) goes in one review.
   Warnings with "Proceed anyway" need a reason ticked to unblock the button.
6. **App pricing**: Monetize → Products → App pricing. "Make your app free"
   is permanent; a sale can run at most 8 days.

Testers Community (`testerscommunity.com`, $15 Starter): Submit App → add
the Google Group as above → app name, Starter plan, opt-in link, square
icon (512×512), tester notes ("no login needed; demo profile under
Settings") → "not a TWA" → buy one credit → Submit App. The service
re-checks the app itself; a paid app or an unreviewed release shows as
"Day 0 / 16" until Play catches up (up to 24 h). After the 14 days: apply
for production access in Play Console, then promote the release.

## 5a. Demo builds (internal testers, the S26)

`bash scripts/build-demo-apk.sh` builds "Flow Demo": the generic flavor
as package `com.moneyflow.generic.demo`, link scheme `flowdemo`, with
`EXPO_PUBLIC_DEMO_CONTROLS=1` baked in, which adds Settings → Demo
controls (Pro on/off, pre-paywall on/off, reset). It installs beside the
store build with its own data, so both can live on the S26. It installs
for the main Android user only (`--user 0`), not the dual/work profile.
Store releases never carry the flag (the group and its code disappear).

The iOS simulator is a dev client, so the same group appears there when
Metro runs with `EXPO_PUBLIC_DEMO_CONTROLS=1` (add it to the start
command; `-c` after changing it, the value is inlined at bundle time).

The script regenerates `android/` as the demo variant; `build-aab.sh`
regenerates it again for a store build. Internal testers get the demo
APK directly (it is not a Play track build); the Play internal track
carries the normal package with license testers for real purchases.

## 5b. Store products (Pro unlock)

Flow Pro is one non-consumable product, bought through expo-iap with no
server. The id must match `PRO_PRODUCT_ID` in `constants/pro.ts`:
`flow_pro_lifetime` (Amanah: `amanah_pro_lifetime`). The paywall shows
the store's own price; until the product is approved the store returns
nothing and the buy button reports "Store unavailable".

App Store Connect:
1. App → Monetization → In-App Purchases → **+** → Non-Consumable.
   Reference name "Flow Pro", Product ID `flow_pro_lifetime`.
2. Price schedule: pick the 9.99 USD tier; Apple fills the other
   currencies. Localizations: display name "Flow Pro", description one
   line. Review screenshot: any paywall capture (1320×2868 works).
3. The first in-app purchase must be submitted **with** an app version:
   on the version page, section In-App Purchases → add it, then submit.
   After that, product changes go through on their own.
4. Testing: Users and Access → Sandbox → add a sandbox Apple ID. On the
   phone, Settings → App Store → Sandbox Account. TestFlight builds buy
   against sandbox for free.

Google Play:
1. Monetize → Products → One-time products → **Create product** (the
   page only opens once a build with the Billing permission is uploaded).
   Product ID `flow_pro_lifetime`, name "Flow Pro", description, price
   9.99 USD → set the other currencies from it. **Activate**.
2. The Billing permission comes from the expo-iap config plugin
   (`android.permission.BILLING` is added at prebuild); a build without
   it cannot see products.
3. Testing: Setup → License testing → add the test Google accounts; they
   buy for free on any track, including internal testing. Purchases made
   by license testers can be refunded from the Order management page.
4. Products only resolve in builds installed from Play (any track), not
   from a sideloaded APK.

Both stores: the paywall's Restore button is required by Apple review;
Play just needs the purchase to be acknowledged (`finishTransaction`),
which the purchase module does, or Play refunds after three days.

## 6. Screenshots

iOS, from the simulator (iPhone 17 Pro Max gives 6.9" natively; downscale
with `sips -z H W` for the other slots):
- Dev build with `EXPO_PUBLIC_BYPASS_ONBOARDING=1 EXPO_PUBLIC_DEV_PROFILE=Demo
  EXPO_PUBLIC_SCREENSHOT_CTL=1`; a dev-only controller polls
  `http://localhost:8090/route.txt` and navigates to whatever route is in it
  (`python3 -m http.server 8090` serving a folder with that file).
- `xcrun simctl status_bar booted override --time 9:41 --batteryState charged --batteryLevel 100 --wifiBars 3 --cellularBars 4`
- `xcrun simctl io booted screenshot out.png`
- Rebuild the demo data first so dates are current (Flow: `demo:rebuild`
  controller command, or Settings → Recreate demo profile).

Android, from a real phone (the emulator starved the laptop's CPU and
crashed): `adb shell am start -a android.intent.action.VIEW -d "<scheme>://<path>"`
opens deep links directly, `adb exec-out screencap -p > out.png` captures.
A Galaxy at 1080×2340 matches Play's phone tier. Samsung ignores the
status-bar demo mode; live with the real clock.

Order and content: Home, Add, Plan, Activity, Accounts, plus the headline
feature. Keep file names stable (`01-home.png` …) so store uploads replace
cleanly.

### Widgets

iOS: `targets/widget/` (SwiftUI, `@bacons/apple-targets`). The target and
the App Group entitlement (`group.<bundle id>`) are generated at
`expo prebuild`; after changing `expo-target.config.js` or `app.config.ts`
run `npx expo prebuild --platform ios --clean` and `npx pod-install`.
The widget reads `snapshot` from the App Group; the app writes it from
`components/WidgetSync.tsx`. Verify with a device archive, the simulator
build is blocked (above).

Android: `modules/flow-widget/` (Kotlin, autolinked; no prebuild needed
for code changes, the manifest receivers merge from the module). Test on
the S26: Settings → Home screen widgets pins one, or long-press the home
screen → Widgets → Flow.

### iOS simulator dev build (known issue, 2026-11-28)

The simulator dev client cannot currently be rebuilt: the ML Kit
text-recognition pods ship plain fat frameworks whose arm64 slice is the
device one and set `EXCLUDED_ARCHS[sdk=iphonesimulator*] = arm64`, so the
simulator must be x86_64, and the prebuilt React Native core (SDK 54) fails
to link x86_64 in Debug (`facebook::react::Sealable` undefined). Ways out,
when it matters: build React Native from source
(`ios.buildReactNativeFromSource` in `ios/Podfile.properties.json`, slow
first build), or make the receipt-scanner pod conditional on device
builds. Until then the old simulator client keeps working with Metro;
native modules added later (expo-iap) are loaded lazily so a missing one
only shows as "store unavailable". `xcodebuild` also cannot list concrete
simulators here; use `-destination 'generic/platform=iOS Simulator'`.

## 6a. Listings and captioned screenshots in twelve languages

English is the source; everything else is generated from it.

- Text: `assets/store/generic/listings/<lang>.json` (name, subtitle, short,
  keywords, full, whatsNew, notes, captions) and `demo-<lang>.json` (the
  sample-data labels that show up in screenshots). `BRIEF.md` there is the
  brief for translating; `check.py` enforces the store limits and the
  "no platform names" rule, so one text serves both stores.
- `python3 scripts/demo-text.py` turns the demo files into
  `utils/db/demoText.ts`; the Demo profile is seeded in the app's language.
- Captures: `bash scripts/capture-shots.sh <ctl dir> <out dir> [lang ...]`
  on the iPhone 17 Pro Max simulator. Per language it sets the app language
  (`kv:locale=…`, relaunch with `-AppleLanguages`), rebuilds the Demo
  profile and walks eight screens: home, add, plan, event, activity,
  insights, accounts, themes (Home in Espresso light). The controller also
  takes `locale:<code>` to switch language in place.
- Compose: `python3 scripts/store-shots.py <out dir> [lang ...]` puts each
  caption over a framed capture and writes `build/store-out/<lang>/<set>/`
  for four sets: `play` 1080×1920, `appstore-6.9` 1320×2868, `appstore-6.5`
  1284×2778, `appstore-6.3` 1206×2622. Not committed; remake at will.
  Caption fonts: Outfit (Latin, Turkish), Helvetica Neue Bold (Russian,
  Kazakh), Hiragino Sans GB (Japanese, Chinese), Apple SD Gothic Neo (Korean).
- App Store locales: en-US, es-ES, es-MX (same Spanish text), pt-BR, fr-FR,
  de-DE, tr, id, ru, ja, ko, zh-Hans. No Kazakh there. Display types for
  the three sets: `APP_IPHONE_67`, `APP_IPHONE_65`, `APP_IPHONE_61`.
  Localizations cannot be added while the version is Waiting for Review:
  remove the submission, edit, submit again (the version and, the first
  time, the in-app purchase).
- Play locales: en-US, es-ES, pt-BR, fr-FR, de-DE, tr-TR, id, ru-RU, kk,
  ja-JP, ko-KR, zh-CN. Store listings → Edit default listing → language
  menu → Manage languages. A new language shows the default graphics greyed
  out until it gets its own. Add assets → Upload puts files in the asset
  library; select them in the panel in the order wanted, then Add.
- Bulk upload, both from the signed-in browser session (section 7):
  `python3 scripts/store/manifest.py` writes sizes and checksums,
  `scripts/store/asc-shots.js` replaces the three App Store sets per locale
  (about a minute per locale), `scripts/store/play-shots.js` fills name,
  short and full description and the eight phone screenshots per Play
  language and saves a draft. Both read their to-do list and the files from
  a local `python3 -m http.server 8091`; the header of each says what to
  serve.
- Look at one contact sheet per language before uploading. The add screen
  is the one that breaks: its prefill is base64 in the route and has to be
  percent-encoded (a "+" arrives as a space and the form opens empty).
- Sending: Play listing → Next → AI asset declaration ("Don't label
  assets": the screenshots are captures) → Save → Publishing overview →
  Submit changes. If a release is already in review, Play asks to restart
  that review. App Store: Add for Review on the in-app purchase page while
  it is not yet approved, then on the version, same draft submission,
  Submit for Review.

## 7. Driving the consoles from a browser session

Playwright MCP works for everything up to the final submit:
- Use `browser_snapshot` to a file and grep it for refs; refs change after
  the page re-renders, so re-snapshot before clicking.
- Role selectors (`role=button[name="Save"]`) survive re-renders better than refs.
- File uploads: click the control that opens the chooser, then
  `browser_file_upload` with absolute paths under the project directory.
- Play's Angular pages render late; wait for a known text before snapshotting.
- The permission classifier blocks publishing clicks ("Add for Review",
  store submit). Prepare everything, then hand those clicks to the user.
- App Store Connect has no API key here, but its own web API answers from
  the signed-in tab: `https://appstoreconnect.apple.com/iris/v1/<path>` with
  headers `Accept: application/json` and `X-CSRF-ITC: [asc-ui]`. Same
  resources as the public API (localizations, screenshot sets, uploads).
  `page.request` in a Playwright script carries the session cookies and can
  also fetch local files from a `python3 -m http.server`, which is how
  screenshots get uploaded in bulk.
- ASC: wait a few seconds after Save before navigating, or the save is lost.
- Play paths: `/app/<id>/one-time-products`, `/app/<id>/store-listings`,
  `/app/<id>/publishing`, `/developers/<dev>/license-tester`.
- Stale `playwright-mcp` processes block reconnects: `pkill -f playwright-mcp`,
  then `/mcp` in Claude Code to reconnect.

## 8. Checklist per release

- [ ] Bump version / buildNumber / versionCode; commit.
- [ ] iOS archive → upload; wait for processing.
- [ ] AAB built and signed with the upload key.
- [ ] ASC: new version, What's New, build, screenshots, age ratings current → Add for Review.
- [ ] Play: release on the right track, notes ≤ 500 chars, listing screenshots → Submit for review.
- [ ] Store products created and active in both consoles (first time only); iOS product attached to the version.
- [ ] Listings and screenshots in all twelve languages (section 6a) when the text or screens changed.
- [ ] Push the release commits.
- [ ] Update `docs/ROADMAP.md`.
